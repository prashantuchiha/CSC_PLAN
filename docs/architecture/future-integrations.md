# Future integrations

These are extension instructions for later phases. Keep provider SDKs and
authentication within their adapters, and inject implementations at `bootstrap.py`.

| Future component | Attach point | Boundary |
|---|---|---|
| OpenAIResearchProvider | `adapters/ai/`, AIResearchProvider | Return provider-neutral ResearchResult, StudyPlanContent and EmailDraft; no SDK types in domain/services |
| MicrosoftGraphEmailProvider / Outlook | `adapters/email/`, EmailProvider | OAuth/token storage and provider message/thread IDs stay in adapter; approval/idempotency live in application workflows |
| Gmail provider | Same EmailProvider | Swap composition binding; research/domain/storage remain unchanged |
| Crawl4AIResearchProvider | `adapters/research/`, ResearchSourceProvider | Search/retrieve source metadata and optional bytes; save snapshots via FileStorage and evidence via services |
| DocxDocumentProvider | `adapters/documents/`, DocumentProvider | Return generated bytes; application uses FileStorage and records StudyPlan version/path |
| Additional MCP host integration | Existing `interfaces/mcp/` stdio server | Configure the host to launch the existing adapter; add only high-value service-backed tools |
| React / Angular frontend | Existing REST API | Use published OpenAPI schemas; pagination/batch jobs are already available |
| Additional job handlers | `workers/jobs/`, JobHandler | Register a focused handler and payload validator through composition; leave worker engine intact |
| Celery / Redis later | JobDispatcher / infrastructure relay | Deliver durable job IDs as wake-up hints; use outbox/polling to bridge commits; business producers stay unchanged |
| Another SQL database | Database adapters / unit of work | Replace driver/model/migration wiring; keep repository behavior and transaction contracts |
| Object storage | FileStorage | Return stable relative/logical keys; consumers do not use pathlib |

## Suggested next iteration

The single-process SQLite worker, fake provider, handler registry, atomic claim, lease, recovery,
bounded retry and review state now exist. Before real providers, add credentials, rate limits,
timeouts and contract tests. Long handlers should heartbeat between bounded external calls;
there is no automatic heartbeat thread. Competing claim attempts, cancellation during execution
and stale completion are tested. Measure SQLite write contention before adding workers.

Provider research must produce sources and candidate facts, then pass them through
ResearchIngestionService. Add an explicit application review policy before treating AI-generated
claims as verified or populating canonical entity fields. ResearchResult is a starting contract;
extend its DTOs when real provider requirements are known instead of exposing raw SDK responses.

Email sending requires a separate explicit approval workflow, durable provider idempotency,
recipient validation, and a record of the exact approved draft. A job type named EMAIL_SEND is
only metadata today. Marking a job COMPLETED does not send anything, and a metadata status must
never be treated as authorization by a future adapter. An email handler must use provider-level
idempotency or reconciliation on retries, verify the exact approved content and handle uncertain
send outcomes. The SQLite claim token cannot guarantee exactly-once delivery outside SQLite.

Keep adapters synchronous until a measured need justifies async. REST uses synchronous handlers
in FastAPI's thread pool; database sessions remain request-operation scoped. A future expensive
task must execute in the worker, not a web request. Start with one worker/concurrent job to respect
the laptop's memory and SQLite's single-writer characteristics.

For any adapter replacement: implement the protocol; reuse service tests with a fake; add adapter
contract tests; change composition; keep credentials in provider-specific settings. Do not import
SDKs in domain/application or bypass services through MCP/frontend handlers.
